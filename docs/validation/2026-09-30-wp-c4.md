# WP-C4: scenes, profile state and macro policy

DI-11 and DI-12 are implemented on `wp-c4-scenes`. Profile recall and scene
profile steps share the same state writer. Scene profile steps run no macros;
explicit scene steps determine the sequence. Disabled outputs still receive
their routing and settings, and an override skips only its selected write.

Scenes accept `wait` steps with a finite duration of 0.5–30 seconds. The editor
can add, remove and save them. Saved macro `continue_on_error` is used unless a
caller explicitly overrides it. Conflict detection compares actual writes,
including defaults, and ignores absent optional settings and skipped writes.

Two adjacent defects were found and fixed: omitted macro timeouts disabled the
documented 300-second deadline (API-26), and editor rerenders accumulated removal
handlers, allowing one click to delete multiple steps (UI-54). Local ESLint
also scanned gitignored artifacts and reference repositories (TST-12).
UI-53's broader editor styling work remains open.

## Regression evidence

Before the core fixes, seven new `tests/test_wp_c4.py` cases failed against the
original code. They cover shared state writes, disabled outputs, enabled
overrides, no implicit macros, wait validation/execution, saved macro policy
and conflicting default values. Simulator tests compare recall and scene
effects, verify wait command timestamps, and inject a single real CEC refusal.

The default-timeout regression failed against the original REST handler:
`execute_macro` received `timeout_s=None` instead of 300. The editor regression
against the original script failed because the launching Settings drawer stayed
open. A second editor regression failed before the delegated-handler fix:
removing one wait left two steps instead of three and deleted the following
macro. Both final editor regressions pass in the pinned Playwright container.
A huge out-of-range integer initially raised `OverflowError` during wait
validation; checking the bounds before converting it now rejects it cleanly.

Ignored diagnostic logs are in `build/c4-*`. Committed scenario records are the
durable proof; their feature links are in `features.yaml` and the generated
ledger.

## Shipped-image proof

The final proof uses a disposable Docker network, fixture data volume, matrix
simulator and `hdmi-matrix-hub:wp-c4`. Chromium drives that image's web UI; the
API client calls the same image. `tools.validate` uses the existing simulator
control URL and hub URL instead of starting another hub process. The records
include the image ID from `docker inspect` and the source commit.

The stack is removed after the run. No real matrix, TV or Remote is contacted.
The wait scenario checks the simulator's timestamps between two actual device
commands. The macro refusal scenario verifies later accepted commands after
one rejection, and the default stop scenario verifies that later commands are
absent. The editor scenario adds two waits, removes one and reads the saved
single wait back through the hub.
