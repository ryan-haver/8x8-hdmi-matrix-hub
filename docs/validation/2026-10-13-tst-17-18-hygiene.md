## 1. TST-18: port-bind collision in `free_port()` and `HubProcess`

### Cause

`tools/validate/stack.py:free_port("127.0.0.1")` asked the OS for an ephemeral
port by binding `("127.0.0.1", 0)` without `SO_EXCLUSIVEADDRUSE` and immediately
closing the socket, then handed that port to the UC-mode hub subprocess. Two
different races followed on Windows:

1. **Wildcard vs loopback interface mismatch (`WinError 10013`).** On Windows,
   when another process (e.g. Docker or Chromium) holds `("0.0.0.0", port)`
   without `SO_EXCLUSIVEADDRUSE`, `bind(("127.0.0.1", port))` still succeeds!
   When the UC-mode hub starts, `src/driver.py:check_port_available(port, "0.0.0.0")`
   sets `SO_REUSEADDR` and calls `bind(("0.0.0.0", port))`, which Windows
   rejects with `PermissionError: [WinError 10013]`.
2. **TOCTOU window (`WinError 10048`).** Between `free_port()` closing its
   probe socket and the hub child binding `api_port` / `uc_port`, another
   process on a busy machine can take that ephemeral port.

### Before (failing-first)

In `tests/validation/test_runner_timing.py` (`build/tst-17-18/failing-first/test_runner_timing.log`):

- `test_free_port_skips_ports_bound_on_all_interfaces` held a socket bound to
  `("0.0.0.0", held_port)` and made the first `("127.0.0.1", 0)` probe land on
  `held_port`. On Windows, `free_port("127.0.0.1")` returned `held_port`, and
  `check_port_available(picked)` then failed with:
  `PermissionError: [WinError 10013] An attempt was made to access a socket in a way forbidden by its access permissions`.
- `test_hub_process_retries_when_an_auto_picked_port_is_taken_before_bind`
  returned a held port on the first `uc_port` allocation. `HubProcess.wait_ready()`
  exited with `RuntimeError: hub exited before ready (rc=1)` and the hub log
  recorded `ERROR:driver:Port <port> is already in use!`.

### Fix

1. `free_port()` (`tools/validate/stack.py`) now probes `("0.0.0.0", port)` with
   `SO_REUSEADDR` (`_can_bind_wildcard`) whenever `host != "0.0.0.0"`, holding
   rejected sockets open until an available port is chosen so the OS cannot
   hand the same port back on the next iteration.
2. `HubProcess` (`tools/validate/stack.py`) tracks whether `api_port` and
   `uc_port` were auto-allocated (`_auto_api_port`, `_auto_uc_port`). If the hub
   child exits before ready and its log shows a port-bind failure (`Port … is
   already in use`, `WinError 10013`, `WinError 10048`, `EADDRINUSE`, or
   `address already in use`), `wait_ready()` allocates fresh ports and retries
   up to 3 attempts.

### After

Both regression tests in `tests/validation/test_runner_timing.py` pass.

## 2. TST-17: slow Windows DNS for `.invalid` in hub subprocesses

### Cause

`tests/uc/test_setup.py::test_setup_errors_name_the_problem` drives the Remote
setup flow against `no-such-matrix.invalid` and expects `NOT_FOUND`. Unlike
`tests/sim/test_sim_login_credentials.py` (fixed in `7dbc4dc` with an in-process
monkeypatch), the DNS lookup in `tests/uc/test_setup.py` runs inside the
`HubProcess` child process (`src/driver.py:_tcp_probe`, which uses a 5.0 s
timeout). When the Windows DNS client takes longer than 5 s to negatively
resolve `.invalid`, `_tcp_probe` times out and reports `TIMEOUT` instead of
`NOT_FOUND`.

### Before (failing-first)

`tests/uc/test_setup.py::test_setup_errors_name_the_problem` injected a
temporary `sitecustomize.py` simulating a 6 s OS resolver delay for `.invalid`
(`build/tst-17-18/failing-first/test_setup_errors_name_the_problem.log`).
The hub subprocess timed out after 5 s and failed the test with:
`AssertionError: assert 'TIMEOUT' == 'NOT_FOUND'`.

### Fix

- Added `tools/validate/_site/sitecustomize.py` and prepended
  `tools/validate/_site` to `PYTHONPATH` in `HubProcess.env()`
  (`tools/validate/stack.py`).
- `sitecustomize.py` first chains any downstream `sitecustomize.py` on
  `sys.path`, then wraps `socket.getaddrinfo` so RFC 6761 `.invalid` hostnames
  fail immediately with `socket.gaierror(EAI_NONAME, "Name or service not known")`
  without querying the host OS resolver. All other hostnames use the real
  `socket.getaddrinfo`.

### After

`tests/uc/test_setup.py::test_setup_errors_name_the_problem` passes in 3.2 s
even with a 6 s slow-OS-DNS stub behind `tools/validate/_site` on `PYTHONPATH`.

## 3. Windows timer quantum in `CommandGap` (`scenes.wait_between_actions`)

### Cause

`scenes.wait_between_actions` runs a scene with a 0.5 s `wait` step
(`asyncio.sleep(0.5)` in `src/scene_execution.py`) between two device commands
and checks `CommandGap("set beep", "video switch", seconds=0.5)`. On Windows,
Python's `asyncio` event loop has `loop._clock_resolution == 0.015625`
(15.625 ms `GetTickCount64` ticks) and fires timers when
`when <= loop.time() + _clock_resolution`. Combined with `round(time.time(), 3)`
in the simulator's command log, a genuine 0.5 s wait legitimately records a gap
of `0.484`–`0.499` s (seen in CI as `0.495s` and `0.499s`).

### Before (failing-first)

`test_command_gap_tolerates_windows_timer_quantum_and_rejects_short_waits`
(`build/tst-17-18/failing-first/test_command_gap.log`) tested `CommandGap(..., 0.5)`
with `0.499 s` and `0.495 s` gaps and failed (`assert 'fail' == 'pass'`).

### Fix

`CommandGap` in `tools/validate/runner.py` allows one Windows timer tick plus
1 ms log rounding (`gap + 0.020 >= exp.seconds`) while still rejecting shorter
waits (e.g. `0.450 s`) or missing commands. Keeping the tolerance in
`tools/validate/runner.py` preserves `simulator_fingerprint()`.
