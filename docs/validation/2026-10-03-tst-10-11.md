# TST-10 / TST-11: status colours in the visual suite, lock test start-up

Test-tooling fixes on `fix-tst-10-11` (owner approved "all fixes", 2026-10-03).
No `src/` or `web/` change and no baseline change. Diagnostic logs and images
are in `build/tst10/` and `build/tst11/` (gitignored).

## TST-10: colour-only status regressions

**Cause.** `toHaveScreenshot` compares pixels by pixelmatch's YIQ distance with
Playwright's default threshold 0.2. The distance between the header pill's red
(`#ef4444`) and the Tron Classic standby orange (`hsl(25 85% 55%)`) is about
0.13 on fully covered pixels, and less on anti-aliased text and the 1 px border,
so no pixel counts as different.

**Before.** A throwaway CSS change, injected just before each capture, recoloured
the status indicators: the reconnecting header pill red (the pre-WP-E1 look), the
kiosk dot (disconnected) orange, input tile bars and connected footer tiles. Run
against the committed baselines at threshold 0.2, at desktop, Tab A11 and iPhone
16 Pro Max: 7 of 24 captures passed, including all four `app/header/*` captures
at desktop and Tab A11 and `kiosk/disconnected` at all three viewports. Only the
large tile bars and footer borders failed.

**Fix.**

1. `tests/e2e/visual/status-colours.spec.ts` runs in every visual project. It
   drives each status state and compares the computed colour with the approved
   value:
   - the header pill, connected, disconnected and reconnecting, in all four presets;
   - the kiosk connection dot;
   - the kiosk input tile status bars: signal, cable, unplugged, unknown and active;
   - the kiosk output footer tiles (border and opacity).

   It reads styles only, so rendering cannot make it flaky. The expected values
   are a table in the spec: `#22c55e` and `#ef4444` for the header, the preset's
   standby colour `hsl(secondary 85% 55%)` for reconnecting, and the kiosk
   palette. Changing a status colour now means changing that table in a reviewed
   change.
2. The screenshot threshold is now 0.05 (`tests/e2e/playwright.config.ts`).
   `visual:update` (`--update-snapshots=changed`) uses the same threshold, so it
   no longer keeps a baseline that differs only in hue.

**Noise floor.** The whole suite (1,003 captures) was re-captured twice in the
pinned container with `--update-snapshots=all` into `build/`. The two captures
were identical at every threshold ≥ 0.02. At 0.01 only 19 files differed, by 4
pixels at most. 0.05 therefore adds no flakiness.

**Stale baselines (TST-14).** At 0.05, the same 48 committed baselines differ from
both re-captures. The page changed below 0.2 after those baselines were approved.
Most changes are in content dimmed behind a modal or beside the main panel, such
as profile list colours behind `editor/profile/*` and next to `outputs/list/*`.
These baselines keep 0.2 through `STALE_BASELINES` in `visual.spec.ts` until the
owner reviews and re-approves them.

**After.** The same throwaway regression, at desktop and Tab A11, failed all 32
checks:

- `app/header/*` failed by 556–563 pixels and `kiosk/disconnected` by 56 pixels.
- Every status-colours test failed, for example "header pill connected
  [tron-classic]: border-top-color should be #22c55e (rgb(34, 197, 94))", received
  `rgb(16, 185, 129)`.

Two further throwaway runs checked the status-colours tests on their own:

- Reconnecting turned red failed in all four presets, for example "should be
  hsl(25 85% 55%) (rgb(238, 124, 43))", received `rgb(239, 68, 68)`.
- Changes too small for any pixel threshold also failed: disconnected
  `#ef4444` → `#f43f5e` (distance ≈ 0.03) and the unknown tile bar
  `#64748b` → `#6b7280` (≈ 0.02).

The throwaway changes were reverted and never committed. With the committed
tree, the full suite (smoke, flows, then every visual project) was run twice in
the pinned container, with 0 failures each time: 1,087 passed and 33 skipped
in both runs (41.5 and 38.8 minutes).

## TST-11: the lock test hung the pytest session

**Cause.** With the Microsoft Store Python, `sys._base_executable` is the
WindowsApps app-execution alias (`st_reparse_tag` 0x8000001B, size 0). A
`CreateProcess` on it can block inside `Popen`, before `subprocess.run`'s
`timeout` applies.

**Before.** `Popen._execute_child` was made to block, simulating the observed
py-spy stack, and the original `_try_in_subprocess` was called
(`subprocess.run(..., timeout=30)`). It was still blocked after 45 s.

**Fix.**

- The children start with the real interpreter, `sys.base_prefix\python.exe`.
  Neither an alias nor the venv launcher is used. If no such interpreter exists,
  the test is skipped with a reason. POSIX keeps `sys.executable`.
- `Popen` runs in a daemon thread with a 30 s bound. When the bound expires, the
  test fails and the session continues; a child that starts late is killed.
- The holder's first output line and the try-acquire child are also bounded.
- A new test checks that a blocked process creation fails within the bound.

**After.**

- The same blocked-creation probe failed at 30.0 s with "process creation
  blocked, TST-11", and the session continued.
- On this machine (Store Python 3.12.10), 20 consecutive sessions of
  `tests/test_process_lock.py` passed each time (7 passed, 1 POSIX-only skip),
  at 1.9–4.1 s per session. Another 20 sessions, run while the visual suite was
  loading the machine, also all passed, at 2.1–4.7 s per session.
- The real cross-process lock is still exercised: the child interpreter is a
  separate process taking the OS lock.
- On Linux (`python:3.12-slim`), 5 sessions each gave 8 passed.

## TST-13, TST-15, TST-16 and TST-17: other tooling fixes on the branch

- **TST-13: `run-in-container.mjs` argument order.**
  - Before: `update --review-dir build/x -- …` passed Playwright a literal
    `--`, after which Playwright ignored every option. The run captured the
    whole suite with the default reporter.
  - After: the same order reaches Playwright as
    `--update-snapshots=all --no-deps --reporter=dot`, and the dot reporter is
    used (1,037 tests).
- **TST-15: `WsObserver` event ordering.**
  - Before: with the wall clock frozen, as between two ~15.6 ms Windows ticks,
    the old `sync()` returned True at once and took the welcome snapshot as its
    answer.
  - After: the new `sync()` returns False after its timeout when no fresh
    answer arrives. Every `since()` caller now marks with `WsObserver.now()`,
    and `since()` refuses a wall-clock mark.
  - `F-CEC-011` (88 `cec_caps` scenarios, simulator, api client) on this
    machine: 86/88 before, with two stale-capability failures (the hub still
    reported the previous output name and connection); 88/88 in both runs
    after.
- **TST-16: per-scenario client address in the api client.** A recording test
  server saw the run-wide address on every request before the fix, and the
  per-scenario addresses after. The rate-limit 429s were not reproduced end to
  end in these runs.
- **TST-17: DNS-dependent test.** Resolving `no-such-matrix.invalid` took 11 s
  on this network, so the test read `timeout` and the pre-commit hook failed.
  The test now makes that one name fail at once; it failed before and passes
  after.
  `tests/uc/test_setup.py::test_setup_errors_name_the_problem` fails the same
  way on this network: the lookup runs in the hub subprocess, so it is
  registered under TST-17 but not fixed.
