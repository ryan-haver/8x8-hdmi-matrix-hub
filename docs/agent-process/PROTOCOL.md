# Phase and wave coordination protocol

Version 1.0.0. Apply with the receiving repository's `REPO_CONFIG.json`, current
user instructions and live state. Preserve stricter compatible target controls;
record conflicts for resolution before affected actions. This kit formalizes an
operating process, not permission to start unrequested work or claim qualification.

## 1. Establish the actual repository and coordinator

Read root instructions, current handoff, development plan and latest validation
baseline. Inspect Git branch, working tree, tracking ref and live remote head.
Preserve unrelated changes. Discover the installed orchestration capabilities and
verify the existing target Run, coordinator binding, all worker-list pages and
inbox before dispatch. Use [ORCA.md](ORCA.md) for the runtime procedure.

Pin the configured integration branch; never assume `main`. Identify protected
worktrees, branches, dirty files and retained resources, including recorded HEADs
and relevant file hashes. They are not staffing slots. Reuse the existing Run;
do not reset it or create a replacement to evade task state or limits.

The coordinator alone owns shared contracts/APIs, root manifests and lockfiles,
canonical acceptance/readiness records and integration conflict resolution.
Workers receive explicit disjoint writable paths. Reviewer reports and scratch
paths are separate from author paths. Maximum three workers plus coordinator,
including review/debate workers; no nested workers or simulated model identities.

## 2. Establish program direction

Before detailed phase preparation, debate phase order, general goals, feature
priorities, dependencies, parallel-ready tracks and the first useful release.
Express timelines as ranges with explicit capacity, review and environment
assumptions; no fabricated velocity or guaranteed dates. Preserve stable phase
IDs or supply a crosswalk for proposed splits.

Use the same three-provider, three-round process below. A documented existing
program decision can be reused when applicable; adoption does not require
redebating completed historical work. A missing provider means provisional
coverage, not invented consensus or a stop to unrelated ready work.

## 3. Prepare every phase through three actual rounds

Reevaluate the phase against the current source and intended outcome. Freeze the
inputs: exact integration/dependency heads, relevant evidence, contracts, goals,
non-goals, entry/exit criteria, environments, risks, implementation strategy,
worktree boundaries, acceptance, recovery and proposed wave order.

At least three real model participants from three verified underlying providers/
families contribute across three rounds. The coordinator synthesizes and does not
count as one of the three independent contributors. Different variants or routers
for one family are not additional independence. Respect configured exclusions.

| Round | Participant responsibility | Evidence barrier |
|---|---|---|
| 1 | Independently assess outcomes, implementation, dependencies, acceptance, risks and task/model/worktree matches against the frozen input | Preserve all reports before sharing peers' reports |
| 2 | Read every peer report, challenge claims and staffing choices, and reconcile findings using source evidence | Preserve full reports and dispositions; synthesize one versioned final plan and allocation |
| 3 | Inspect the same complete final packet and hash; explicitly accept, require changes or report blocked | Record each actual decision, input/report hashes and unresolved dissent |

Consensus requires explicit acceptance from every required participant against
the same final packet and no unresolved material blocker. It is not a majority
vote, a model label or a timer. Agreement does not replace qualified source review
or required environment admission. Preserve rejected findings and prior packets.

Use `CONSENSUS.template.json` and the phase plan shape. Separate debate status
from technical release status. Capacity-limited coverage is `provisional`, with
its missing contributions named. Start useful contributions with available
providers, stagger turns and add perspectives as capacity permits. Preserve report
lineage when replacing a panel member; do not repeat useful rounds solely for a
capacity substitution. Keep technically ready work moving within accepted bounds.
Concrete correctness/dependency blockers and missing qualified review hold the
affected deliverable; they do not justify inventing acceptance.

## 4. Match models to actual tasks and worktrees

Every phase needs a fresh per-task matrix. Evaluate relevant candidates across
the phase, including newly available models; compare plausible alternatives for
each task rather than benchmarking the entire catalog against every small task.
No old roadmap assignment confers permanent ownership.

Each task row records:

- Goal, language/component, difficulty, consequences of failure, dependencies,
  target platform/tool requirements and exact acceptance commands.
- Exact provider/model/route, supported effort or explicit unknown, relevant
  task competence, alternatives and why the selection fits this scope.
- Author and independent reviewer families, review scope/competence, capacity
  reserved for review and corrections, and conflict-of-interest checks.
- Worktree/branch reservation, exact base, exclusive writable paths, prohibited
  shared paths, environment prerequisites and actual launch evidence when known.
- Applicable quota/reset evidence, expected demand, monitoring checkpoints and
  accepted fallback author/reviewer combinations.

Catalog presence, user-reported access, authentication, supported exact launch,
observed effective response and qualified task scope are separate facts. Verify
aliases and preview/stable/router distinctions. Do not infer zero cost/unlimited
usage from subscription metadata. No unsupported model/effort flags or silent
fallback to an inherited default. Underlying model identity, not the API format
or provider label alone, determines family independence.

Use observed source fidelity, implementation quality, assertion strength, tool
competence and scope discipline. Vendor claims are hypotheses until demonstrated
for the assigned scope. Useful bounded tasks with independent evaluation can
establish competence; do not create ceremonial work or automatic exam retries.
Authorship competence is not review competence. Preserve failed qualifications
and do not relabel them as PASS after a provider or account change.

## 5. Monitor capacity throughout the phase

The active coordinator owns quota tracking and placement. Define a modest check
cadence per phase, plus checks before dispatch, at worker checkpoints and after
quota/rate-limit events. Use supported usage interfaces; record observation time,
provider-update time, exact pool/window, remaining allowance if exposed, resets,
shared commitments, expected demand and evidence source. Never read credential
stores or publish private account details.

Below 30% is a sizing signal, not a prohibition. Compare available absolute budget
where exposed, resets, active demand and review/correction reserve. Unknown,
stale or unmapped quota stays explicit. An existing authorized route can take a
bounded monitored task with conservative demand and a preservation/fallback plan;
this does not authorize new spending, accounts or keys. Actual refusal/exhaustion
affects that task; continue other ready work.

Prefer assigning queued work and the next package to suitable available models
before interrupting productive work. Use accepted fallbacks, preserve scarce
specialist capacity, and avoid repeated changes on small meter fluctuations.
Record decisions and outcomes in a ledger, using `CAPACITY_EVENT.template.json`.
Account for shared provider pools; model variants do not multiply quota. Unknown
other-host demand is not zero demand. Do not invent cost or token forecasts.

No extra LLM worker is required for bookkeeping. This policy is active coordinator
behavior, not an installed background service. A persistent monitor/scheduler is
a separate implementation task with ordinary acceptance and independent review.
Do not promise monitoring after the coordinator stops running.

## 6. Hand over unfinished work safely

Use bounded task/checkpoint boundaries where possible. Request a handback with
exact head, dirty/untracked files, ownership, commands/results, findings and
remaining work. Preserve all artifacts and original author/model identities.
Partial work is not successful completion.

Establish honest prior-Dispatch settlement and resource disposition, or follow
the installed recovery guide after positively evidenced failure/exit. Prove the
previous writer cannot continue before granting replacement ownership. Silence,
timeout, a quota badge, TUI idle, missing heartbeat or contact loss alone is not
proof of exit. Never launch a duplicate writer into an uncertain worktree.

Pin the preserved checkpoint and explicitly transfer only the remaining paths
and task scope to a fresh supervised Dispatch. Recheck route/effective response,
task competence, current capacity and independent review. A reviewer cannot
approve material work it authored before or after a switch. Relabeling the new
author does not erase the old one. Do not resume unsupported model selection
inside an existing agent by assumption.

An explicitly accepted same-role fallback can be used after documented
revalidation if scope, competence and independence remain intact. Material changes
to outcome, contracts/security assumptions, strategy, dependencies, ownership,
author/reviewer family allocation or acceptance require a fresh three-round cycle
for the affected plan unless that exact fallback was already accepted. Ordinary
covered corrections/wave splits do not require ceremonial repeats. Capacity
pressure does not authorize failed-qualification retries or weaker review.

## 7. Dispatch a wave and supervise actual workers

Before every wave, revalidate the phase decision, task matrix, live base,
dependencies, environment admission, routes, quotas and review capacity. A moving
integration head within the accepted plan is not itself a new phase debate.
Reservations are not running workers. Fill actual Task/Dispatch/worktree/terminal
and requested/effective model identities from runtime evidence, never guesses.

Use real supervised workers in isolated worktrees. A bare agent session is not
supervised Task/Dispatch authority. Establish exact worktree placement before
writing; do not let two tasks own shared paths. Maintain one coordinator inbox
consumer, fully paginate fleet state and process every delivered message.

Reply to blocking questions, validate `worker_done` against the expected active
Dispatch, and immediately reuse for an authorized follow-up, explicitly retain
when requested, or release the settled worker before acknowledging the delivery.
Do not leave settled resources waiting for integration or archival. Process valid
completions promptly even when an older question is also pending; do not ack
unhandled messages. Lifecycle success and technical acceptance remain distinct.

## 8. Independently review and integrate

Every new implementation deliverable, including fixtures, tests and tooling,
requires qualified independent review from a different underlying model family
before acceptance. Same-family specialist advice can supplement that review.
Missing qualified review holds acceptance of the affected package, not unrelated
ready work. A planning debate does not qualify a source reviewer.

Pin exact author base/head and inspect all commits, actual diff, relevant callers,
generated changes and out-of-scope files. Review behavior and assertion strength,
not just summaries, labels, hashes or passing tests. Use meaningful positive and
negative cases; mutation/equivalent/restored controls when needed for confidence
in consequential assertions. Avoid tests that merely restate implementation.

Record precise findings, severity, source location, evidence, impact and required
correction. Reviewers report; authors fix. Re-review exact corrected source.
Coordinator alone integrates accepted packages sequentially, preserving original
authorship and accepted source equivalence. Material integration changes need
independent review. Run the target's complete applicable combined verification,
using its real stack and configured commands. Record command, environment, exit
status, actual tests/assertions, skipped checks and limits without inflated counts.
Documentation maintenance needs applicable document checks, not unrelated builds.

## 9. Preserve, clean up and verify publication

Every task needs an explicit actual outcome and settled-resource decision.
Before destructive cleanup, preserve exact branch/head, dirty patches, tracked
and untracked artifacts, relevant ignored/non-target files, provider/native
transcripts where available, sanitized lifecycle/test/quota/review receipts and
a full verified Git bundle. Record hashes and any transcript clipping or missing
data. A bundle alone cannot preserve untracked files; do not claim lossless
preservation when evidence is incomplete.

Publish each task branch and independently verify its exact remote head before
removing its worktree. Use Orca-managed removal for Orca-managed worktrees after
release and preservation; follow supported recovery when uncertain. Do not use
raw recursive deletion/pruning, kill shared services or delete protected/user work.
Delete only exact proven completed local task branches after preservation and
publication. Preserve remote task branches; no force push or global cleanup.

Verify the combined source, update the phase baseline, allocation ledger and
current handoff, then commit/push to the configured integration branch. Verify
local HEAD equals tracking ref and a fresh live remote query. Check working-tree
status, every fleet page and coordinator inbox. A pending push, unsettled task or
unresolved managed cleanup keeps that wave open. Do not fan out the next execution
wave until this closeout is complete. Use `CLOSEOUT.template.json` for evidence.

If target policy does not authorize publication, prepare the reviewed change and
record publication pending. Ask only for the missing authority, explain its source
and keep dependent wave launch pending; do not invent permission or ask again when
the existing session already authorizes it.

## 10. Preserve honest state and continuity

Keep the target project's real readiness flags and canonical test gates unchanged
until qualifying implementation, actual execution and independent acceptance
justify updates. Do not create source-project-specific production flags in the
target. Unknown, pending, not-run and failed outcomes retain their meaning.

After each wave, record observed model quality, findings, discipline, time/usage
where available and unresolved blockers for the next phase. Keep a concise current
handoff at the top; mark old snapshots historical. Preserve evidence rather than
repeating outdated state as current. Future coordinators must reconstruct live
authority and repo state before taking over.
