## CR01: response, ownership and shutdown decision

P handler creates a task per `get_status` into global `_replies`; socket finally removes the stream client but does not own/drain those reply tasks. The accepted component supplies bounded application/owner admission, factory rejection without coroutine creation, reserved-count accounting, strong references and truthful cancellation/drain outcomes. Its unchanged bytes retain their exact component acceptance. The current test asserting the handler remains unwired is a historical boundary assertion that a future wiring package must intentionally replace, not silently count as a wiring test.

`WEBSOCKET.md` promises a fresh read after `get_status`, announces changes first and documents errors for malformed/unknown/read failure. It does not document overload rejection or merged response cardinality. The runner `WsObserver.sync()` accepts the first status/error after its message index; that index is not a request identifier or proof the read began after the request. Browser requestStatus sends without per-request correlation; failed switch/recall handling also invokes it. Both policy choices must document busy/error/synchronization behavior and check these callers under load. Existing status/error schema alone proves neither freshness nor compatibility.

Recommended policy for the final plan: admit one active read per socket plus an explicit finite application limit; rejected work gets a sanitized busy error through existing bounded stream transport, with no per-rejection task and no unbounded retry queue. The numerical application limit must be frozen with the coordinator's contract, justified by bounded resource/latency controls, not guessed from a unit-test count. A slow client can exhaust the stream's 256-entry queue and be dropped; queue saturation must not produce a growing close-task list or block another client. The existing queue-drop path removes the client before scheduling close, which is relevant evidence but still needs combined network tests. Busy handling must not create a tight client retry loop or be swallowed as a successful synchronization.

Anthropic's alternative remains technically valid to evaluate: one active read plus a dirty/trailing flag can schedule a read whose start is later than requests accumulated during the first read, without editing the component. It is not necessarily a shared stale snapshot. However, a request during the trailing read may need another read; “at most two” holds only for an appropriately bounded burst interval, not sustained traffic. Waiting-owner sets/flags and cross-socket shared tasks need explicit finite bounds. A shared app refresh cannot be cancelled merely because one socket leaves. An old in-flight reply must not be treated as the newer request's completion; the uncorrelated existing caller is a material compatibility issue. If final R3 selects this policy, specify those semantics and controls instead of calling it unchanged behavior. This is a coordinator planning/contract decision, not an invented owner-only gate.

Shutdown must be checked through actual entry points. `RestApiServer.stop()` stops EventStream before runner cleanup, while runtime stop fences operations and tears down integration/refresh work before stopping its API server. Merely appending an aiohttp cleanup context cannot establish the required earlier WS admission fence. Bind ownership to the actual application/stream rather than the module-global getter; test two applications and two sockets independently. Specify idempotent early admission closure, cancellation requests, bounded waits and truthful remaining-task reporting before releasing dependent stream/runtime/client resources; cancellation resistance remains visible, not relabeled drained. Cover direct app cleanup, direct server stop, runtime stop, start failure and repeated stop. Do not change accepted drain semantics to hide lifecycle defects.

Negative controls must hold the read pending, flood one and several sockets, close one socket, prove the other still responds, saturate send queues, force read errors/cancellation resistance, stop during admission/factory execution, and verify no orphan tasks, stale replies or cross-app cancellation. Measure command progress while refresh is saturated: runtime refresh and writes share the transaction lock, so bounds alone do not prove acceptable command latency. Freeze deterministic ordering/event assertions and a justified latency limit; no production denial-of-service magnitude or latency result is measured here.
